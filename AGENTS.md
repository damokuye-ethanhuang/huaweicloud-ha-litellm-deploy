# AGENTS.md — agent contract

You are deploying LiteLLM on Huawei Cloud from this repository. Read this file
fully before running anything. It is the authority on *what you may do*; the
code is the authority on *how*.

## Golden rules

1. **One input file.** `deploy-inputs.yaml` is the only file a human fills in.
   Never edit `terraform.tfvars`, `out/*`, or chart values by hand — they are
   generated by `scripts/preflight.py` on every run.
2. **Never fabricate.** If a required value is missing, ask the operator for it
   using the item's `help` text. Do not invent CIDRs, certificate IDs, VPCEP
   service IDs or AK/SK.
3. **Never skip the plan.** `apply-infra` refuses to run without a saved
   `tfplan`. It is legitimate to run `plan`; it is a policy violation to run
   `terraform apply -auto-approve` directly.
4. **Secrets never enter arguments, files or logs.** AK/SK live in
   `secrets/hw.env` (written by `creds.sh set`, gitignored) or in the
   environment; never paste them into a chat, a commit or `deploy-inputs.yaml`.
   Generated passwords are the job of Terraform. Provider API keys belong in
   `secrets/app.env` (gitignored). When you display output from Terraform,
   redact values of type `sensitive`. After a test, `handoff.py scrub` then
   `handoff.py check` must pass.
5. **Stop on failure.** Each stage either succeeds or stops. Do not "work
   around" a failed stage by deleting resources, editing state, or disabling a
   check. Report the failing stage and the exact error.
6. **Internal only.** This reference design is private-only: the ELB has no EIP,
   `client_cidrs`/`admin_cidrs` must be private ranges, and there is no public
   MaaS endpoint. If a user asks to expose it publicly, that is a design change
   requiring a new review — say so, do not patch it in.

## The deployment loop

```
preflight → plan → [operator review] → apply-infra → deploy-app → verify
```

| Stage | Command | You may run it | Notes |
|---|---|---|---|
| preflight | `./scripts/deploy.sh preflight` | always | offline-checks + renders artifacts |
| plan | `./scripts/deploy.sh plan` | always | saves `tfplan`, costs nothing |
| apply-infra | `./scripts/deploy.sh apply-infra` | **only after** the operator has reviewed the plan | 20–40 min, dominated by CCE |
| deploy-app | `./scripts/deploy.sh deploy-app` | after apply-infra succeeds | runs migrations as a hook |
| verify | `./scripts/deploy.sh verify` | after deploy-app | readiness + model list |
| all | `./scripts/deploy.sh all` | **never unattended** | runs everything including apply |

To deploy a single stage again after fixing something, call that stage only.
Every stage is idempotent.

## How to collect missing inputs

Run:

```bash
python3 scripts/preflight.py --json
```

Then read `results[]` with `status == "fail"`. For each failing `key`, look it
up in `deploy-inputs.yaml` and use its `help` field to ask the operator one
question. Group related questions (all network CIDRs together, all TLS items
together). Do not ask about secrets — those are generated.

A ready-made table of every parameter (for pasting into a chat or a ticket):

```bash
python3 scripts/inputs-table.py            # Markdown
python3 scripts/inputs-table.py --format csv
```

## What each check means

| preflight check | Meaning | Your action |
|---|---|---|
| `region` HTTP 404 | region code does not exist | ask for a valid region |
| CIDR rejected | public CIDR or outside VPC | ask for a private CIDR inside `vpc_cidr` |
| `certificate_id` fails format | operator pasted a name, not an ID | ask for the UUID from SCM/ELB |
| `litellm_version > preset` | upgrade gate | point to `docs/upgrade-procedure.md`; only after the operator confirms, rerun with `ACK_UPGRADE=1` |
| `litellm_version > max_compatible` | needs a repo update | stop; explain that `version-presets.yaml` must be updated with evidence |
| `credentials` fail | AK/SK not exported | ask the operator to export them in their own shell; never ask them to paste secrets into the chat |
| `grafana_endpoint` unreachable | expected outside the VPC | warn, do not block |

## Model list

`deploy-inputs.yaml` → `models:` is an array; any number of entries. Required
per entry: `name`, `model`, `mode`. Optional: `api_base` (omit for ModelArts
VPCEP), `max_tokens`, `rpm`, `tpm`. `api_key_env` names an environment variable
that must exist in `secrets/app.env`; the key itself is never written to the
inputs file.

When the operator says "add another model", append to the array — never replace
the existing entries — then rerun preflight and `deploy-app`.

## Version gate

Read `version-presets.yaml`. `preset` is the validated baseline.

- version == preset → proceed;
- preset < version ≤ max_compatible → require `docs/upgrade-procedure.md`
  completion, then `ACK_UPGRADE=1`;
- version > max_compatible → refuse; the preset file itself must be updated with
  release-notes review, migration timing on a restored database, and a
  successful readiness + inference check.

`ACK_UPGRADE=1` is an acknowledgement, not an override.

## Things you must never do

- `terraform apply` without a reviewed `tfplan`
- `terraform state rm`, `state push`, or hand-editing `.tfstate`
- deleting the `litellm-secrets` Secret (it holds the salt key — provider
  credentials become unreadable)
- rotating `LITELLM_SALT_KEY` after models exist
- adding `0.0.0.0/0`, an EIP, or a public listener to make something "work"
- committing `secrets/app.env`, `*.tfvars`, `.terraform/`, `out/`, kubeconfigs
- running `scripts/destroy.sh` without explicit, per-session operator
  confirmation (`CONFIRM=yes` must come from them, not from you)
- installing tools from the internet on the operator's behalf without saying so

## When something fails

1. Re-read the failing stage's output; the scripts print the next command to run.
2. Consult `docs/troubleshooting.md` — it maps the common failures (migration
   job, image pull, 502 from the ELB, 503 from readiness) to causes.
3. If the fix requires changing an input, change `deploy-inputs.yaml`, not the
   generated artifacts, then rerun from `preflight`.
4. If the fix requires changing infrastructure code, stop and tell the operator;
   that is a code change, not a deployment step.

## Reporting

Report, in this order:

1. the stage that ran and its exit status;
2. what actually changed (resource count from the plan, not a narrative);
3. what was verified with real output (readiness payload, model list);
4. what is still unverified (anything requiring a live account you could not
   reach).

Never report success for a stage you did not run.

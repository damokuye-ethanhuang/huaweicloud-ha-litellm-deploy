# Credentials: getting AK/SK into the run without leaking them

The AK/SK is the only secret a human has to supply. Everything else — the
database password, the LiteLLM master key and salt key, the Redis password — is
generated by Terraform. This page is the long version of
[`secrets/README.md`](../secrets/README.md): how to hand the key over, what it
touches on disk, how to prove it is gone afterwards.

## The rules, and why they exist

1. **Never on a command line.** `terraform apply -var access_key=...` is visible
   in `ps` to every user on the host, lands in shell history, and is repeated
   verbatim in CI logs.
2. **Never in `deploy-inputs.yaml`.** That file is tracked; preflight would also
   render the value into `out/terraform.tfvars`.
3. **Never in a chat, ticket or screenshot.** If it reaches one, treat it as
   leaked and rotate it in IAM — deleting the message does not delete the log.
4. **One place on disk, mode 0600, outside the repository.** `$LITELLM_DEPLOY_HOME`
   (default `~/.litellm-deploy`) exists so that `zip -r`, `git add -f` or a
   shared home directory cannot carry the key away.

## Precedence

```
HW_ACCESS_KEY / HW_SECRET_KEY in the environment   (wins)
        ↓
$LITELLM_DEPLOY_HOME/secrets/hw.env                (0600 file)
        ↓
~/.huaweicloud/credentials                          (SDK profile)
```

Environment wins so a CI runner can inject a short-lived credential without
writing anything to disk. It also means **an exported key outlives the file**:
`creds.sh clear` removes the file, but a variable already exported in your shell
still counts as a live credential — that is why `creds.sh check` fails on it and
tells you to `unset`.

## The four ways to supply it

| Path | What lands on disk | Use it when |
|---|---|---|
| `./scripts/creds.sh set` | `hw.env` 0600 | normal case, interactive terminal |
| `export HW_ACCESS_KEY=… HW_SECRET_KEY=…` | nothing | CI, or an agent that runs as a service |
| `./scripts/creds.sh set --from-env` | `hw.env` 0600 | values already exported, non-interactive |
| `~/.huaweicloud/credentials` | SDK profile | `hcloud`/SDK already configured on the host |

### 1. `creds.sh set` — a real session

```
$ ./scripts/creds.sh set
AK (input is hidden):                     ← typed, not echoed
SK (input is hidden):                     ← typed, not echoed
project id [blank = default project]:     ← Enter
[ ok ] stored in /home/opt/.litellm-deploy/secrets/hw.env (AK ****)
[warn] after testing run: ./scripts/creds.sh clear
```

- Input is read with `read -rs`: nothing appears on screen, and a shoulder-surfer
  sees only the prompts.
- `project id` is optional. Leave it blank to use the project the AK belongs to;
  fill it only when the key must act on a different project.
- **An agent cannot run this for you.** `set` refuses when stdin is not a
  terminal, on purpose:

  ```
  $ ./scripts/creds.sh set </dev/null
  [fail] stdin is not a terminal; use --from-env or edit ~/.litellm-deploy/secrets/hw.env
  ```

The file it writes:

```
# Written by scripts/creds.sh on 2026-10-26T16:47:05+03:00. Gitignored; clear it after testing.
HW_ACCESS_KEY=***
HW_SECRET_KEY=***
HW_PROJECT_ID=
```

`chmod 600`, and the script strips surrounding whitespace or a stray `\r` from a
Windows copy — that failure otherwise shows up much later as an opaque signature
error:

```
$ HW_ACCESS_KEY=' ak001 ' HW_SECRET_KEY=$'sk002\r' ./scripts/creds.sh set --from-env
[warn] stripped surrounding whitespace/CR from the pasted value
[ ok ] stored in /home/opt/.litellm-deploy/secrets/hw.env (AK ****)
```

### 2. Environment variables

```bash
export HW_ACCESS_KEY=***
export HW_SECRET_KEY=***
./scripts/deploy.sh plan
```

For an agent that runs as a service, put them in **its** environment, not in the
shell you happen to have open — a service's shell is not your shell. With Hermes
that is `~/.hermes/.env` followed by a restart of the process; the tool subprocess
inherits what the service was started with.

Trade-off: from then on the value is in the process environment, so any `env`,
`printenv`, crash dump or child-process log can surface it. Prefer the file for
anything longer than one session.

### 3. Import an existing export

```bash
export HW_ACCESS_KEY=*** HW_SECRET_KEY=***
./scripts/creds.sh set --from-env
```

Same file, same mode; useful in a bootstrap script that cannot prompt.

### 4. SDK profile

If `~/.huaweicloud/credentials` already holds

```ini
[default]
ak = ***
sk = ***
```

the Terraform provider reads it and no `HW_*` variable is needed. This is the one
path where the key is not in the form this repository manages, so `creds.sh
clear` cannot remove it — clean it yourself if the host is shared.

## What `status` shows, and why it is safe to paste

```
$ ./scripts/creds.sh status
credentials file  /home/opt/.litellm-deploy/secrets/hw.env
                 present
source           file
HW_ACCESS_KEY    ****
HW_SECRET_KEY    ****
HW_PROJECT_ID    (default project)
state            configured
```

The masking rule: empty → `(empty)`; 8 characters or fewer → four asterisks;
longer → first four + `...` + last four. A real AK (about 20 characters) shows as
`HPUA...1KCH`; a 40-character SK is still only four characters at each end.

`status` is the thing to paste into a ticket. It proves presence, source and
project without revealing enough to use.

## Four ways to fail, and the fix

| Message | Cause | Fix |
|---|---|---|
| `creds.sh: command not found` | `.` is not on `PATH`; you are in `scripts/` (or the wrong directory) | `./scripts/creds.sh set` from the repo root, or `./creds.sh set` from `scripts/` |
| `Permission denied` | exec bit lost — copied from a FAT/NTFS mount or a zip that dropped modes | `chmod +x scripts/*.sh` |
| `No such file or directory` although the file is there | CRLF line endings (`#!/usr/bin/env bash\r`) | `sed -i 's/\r$//' scripts/*.sh` |
| `stdin is not a terminal` | ran under CI, a pipe, or an agent tool | run it in a real terminal, or use `--from-env` |

Diagnose all four at once:

```bash
cd ~/workspace/huaweicloud-ha-litellm-deploy
pwd
ls -l scripts/creds.sh                     # needs -rwx…
head -1 scripts/creds.sh | od -c | head -1 # must end with \n, not \r\n
```

## Proving it is gone

```bash
./scripts/creds.sh clear                 # removes hw.env
unset HW_ACCESS_KEY HW_SECRET_KEY        # if they were exported anywhere
./scripts/creds.sh check                 # exit 0 only if neither is reachable
./scripts/handoff.py scrub               # remove other runtime artifacts
./scripts/handoff.py check               # must print "clean"
```

`check` deliberately inspects the environment as well as the file: a credential
exported in a forgotten shell is still a live credential.

## Two deployments on one host

Point `LITELLM_DEPLOY_HOME` at a different directory per checkout and the
secrets, rendered artifacts and bastion keys stay apart:

```bash
export LITELLM_DEPLOY_HOME=~/.litellm-deploy-acme
./scripts/creds.sh set
```

Without it, the second project silently reuses the first one's `hw.env`.

## Windows and WSL2

Everything above assumes a POSIX terminal. Under WSL2 the file lands in the WSL
filesystem with mode 0600 and behaves exactly as on Linux. In Git Bash the
`chmod` is a no-op on `/c/...` paths and `creds.sh set` may work while the file is
readable by other Windows users — one more reason the supported Windows path is
WSL2 (see the platform table in the [README](../README.md)).
